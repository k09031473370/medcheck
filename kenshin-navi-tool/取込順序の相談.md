# 相談：当日データを健診ナビに入れる順序をどうするか

受付アプリを作ってもらっている側（健診ナビ連携ツール担当）からの相談です。
受付アプリの仕様変更をお願いしたいわけではなく、**運用の順序について意見が聞きたい**のが主旨です。
最後に受付アプリ側へのお願いが3つあります。

---

## 1. 状況

2026年10月、福生市商工会の巡回健診。

| 受診日 | 人数 | 健診ナビへの予約登録 |
|---|---|---|
| 10月2日 | 103人 | **86人 登録済み** / 17人 未登録（カナ氏名が無く取込に弾かれた） |
| 10月6日 | 85人 | 未登録 |
| 10月7日 | 65人 | 未登録 |
| 合計 | 253人（名簿は325人分） | |

当日は受付アプリで受付し、`GET /api/navi.json` でJSONを出す。
それを健診ナビに反映するツール（PowerShell）はできている。

**当日夜にやらないといけないこと**
受付番号を健診ナビに入れる。これができないと**血液の検体検査依頼が出せない**。
（検査センターへ検体と一緒に出す。ここが当日のクリティカルパス）

---

## 2. 困っていること

予約を**事前に日付を決めて**登録してあるため、受診日が動いた人でズレる。

> 10月6日予定の人が、都合が悪くなって10月2日に来る（実際に起きる）

```
健診ナビ : 「10月6日の予約」として存在
受付アプリ: 10月2日に受付、受付番号 3番
```

ここで10月6日の予約に「2日の3番」を書くと、同じ日に番号が重複し、
日付で切った検体依頼からその人が抜ける。事故になる。

→ ツール側で**受診日が一致しないときは受付番号を書かない**ようにした（★付きで一覧に出す）。
安全にはなったが、その人は手作業になる。

---

## 3. 順序を逆にする案

当日来た人だけを、**来た日で**登録する。

| | 現在（事前登録） | 逆順（事後登録） |
|---|---|---|
| 事前 | 予約取込Excelを作って健診ナビに登録 | 何もしない |
| 当日 | 受付アプリで受付 | 受付アプリで受付 |
| 当日夜 | 受付番号・カナ・生年月日を書き込む | JSON → 予約取込Excel → 健診ナビに登録 → 受付番号を書き込む |

### 逆順の利点（大きい）

1. **受診日のズレが原理的に起きない**（来た日で作るので）
2. **カナのない17人の問題も消える**（当日カナが分かってから登録する）
3. **オプションを反映できる**
   これが一番大きい。健診ナビの予約取込フォーマットには「オプション検査1〜10」の欄がある。
   そこに書けば、健診ナビが料金行（T_RYOUKIN）と検査行（T_KENSA の親行・子行）を正しく作る。
   現在の事後反映では、ツールがその行を自分で作る＝健診ナビ内部の処理を再現することになるため見送っていた。
   逆順なら行を作るのは健診ナビなので、普通の作業になる。
4. コース変更も同じ理由で自然に入る

### 逆順の欠点（これが本題）

**当日夜に失敗したとき、復旧できない。**

| | 当日夜に取込が失敗したとき | 手で復旧できるか |
|---|---|---|
| 事前登録 | 予約はある。受付番号だけ入っていない | 健診ナビの画面で番号を手入力。103人を2人で30分程度。**検体依頼は出せる** |
| 逆順 | 予約が1件も無い | 33列×103人の手入力。**事実上不可能** |

平常時は逆順のほうがきれい。異常時は事前登録のほうが安全。
クリティカルパス（検体依頼）が当日夜にあるので、**異常時を基準に選ぶべき**だと考えている。

### もう一つの欠点

10月2日の86人は既に事前登録済みなので、逆順に切り替えても**この86人だけは例外**になる。
2日に来なかった人が6日に来ると、2日の予約を取り消すか日付を動かす手当てが必要。
つまり逆順にしても問題はゼロにならず、「325人分」から「86人のうち日を移した人だけ」に縮むだけ。

---

## 4. 現時点の案

1. **10月2日は現在の形のまま**（前夜に方針を変えない）
2. **2日を予行演習にする** — カナの無い17人だけを当日データから予約取込してみる。
   小さいので失敗しても17人を手入力すれば済む
3. **6日・7日をどうするかは10月3日に決める** — 2日の実績を見て。4日間の余裕がある
4. 今夜、受付結果取込ツールをプレビューモード（何も書かない）で流して動作を確認する

---

## 5. 聞きたいこと

1. **この順序の判断についてどう思うか。** 見落としている失敗モードはあるか。
2. 「平常時の美しさ」より「異常時の復旧可能性」を優先する考え方は妥当か。
   それとも逆順にして、別の形で安全網を張るべきか（張るならどんな形か）。

---

## 6. 受付アプリ側へのお願い（3つ）

### ① 受付番号の一覧を印刷できるようにしてほしい（優先度：高）

健診ナビへの取込が失敗したときの最後の手段です。
**アプリ単体で完結する**ことが重要（DBも健診ナビも使えない状況を想定）。

```
2026年10月2日 受付番号一覧
受付番号 / 氏名 / カナ / 生年月日 / 事業所 / コース
     1   山田太郎   ﾔﾏﾀﾞﾀﾛｳ   1975-04-01   ○○工業   A
     2   ...
```

これが紙で手元にあれば、健診ナビに手入力して検体依頼を出せます。
画面表示でも、印刷用HTMLでも、CSVでも構いません。

### ② 当日分だけに絞ったJSONを出せるようにしてほしい（優先度：中）

今の `navi.json` は名簿全員（325人）が入ります。
`GET /api/navi.json?date=2026-10-02` のように、
**その日に受付した人だけ**に絞れると、当日夜の作業が分かりやすくなります。
（絞れなくてもツール側で処理できるので、余裕があれば）

### ③ DBの準備（優先度：高・10月2日の朝まで）

今もらっているサンプルJSONの状態です。

| 項目 | 現在 | あるべき姿 |
|---|---|---|
| 人数 | 310人 | **325人**（名簿が更新されている） |
| カナ氏名 | 0人 | 列として持てるようにしてほしい（入力は当日） |
| 生年月日 | 入っている | そのまま |
| テスト受付 | 10件（9月26日の受付、番号 1・2・1001） | **全部消す** |
| 受付番号の次の値 | 5 | **1に戻す** |

テスト受付が残っていると、ツール側が「受診日が違います」で全部弾きます
（安全側に倒れるので事故にはなりませんが、当日の一覧が読みにくくなります）。

---

## 7. 確認したこと（参考）

サンプルJSONを見て確認しました。

- `reception_number` が入っている人には、必ず `checked_in_date` も入っている
  （番号の無い6人は受付日も空）→ 日付で判断する作りが機能する
- `derived.date_changed` は出ているが、ツール側はこのフラグに頼らず
  **健診ナビの予約の受診日と `actual.checked_in_date` を自分で比べる**ようにした
  （フラグの計算が変わっても壊れないように）

オプションの記号と健診ナビのコードの対応は確認済みです。

| 記号 | コード | 記号 | コード |
|---|---|---|---|
| D | OPJ014 | J | OPJ009 |
| E | OPJ011 | K | OP0008 |
| F | OPJ017 | L | OPJ015 |
| G | OPJ018 | M | OPJ010 |
| H | OPJ019 | N | OPJ020 |
| I | OPJ004 | O | コードなし（反映しない） |

便の本数は項目としては同じ（1本でも2本でも同じ検査）で、
違うのは結果の値の個数だけなので、取込の形には影響しません。
