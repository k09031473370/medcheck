# 新島: 当日追加した血液オプションを健診ナビの既存予約へ入れられるか

作成 2026/11/07。調査だけ。健診ナビへの書き込み・取り込みはしていない。

## 1. 結論（いま分かっている範囲）

- **ツールで入れることはできるが、健診ナビの画面がやっている処理（料金明細・検査の行・印・連番・金額）をまねて作ることになる。**
  福生ではこの理由で見送り、「★オプション変更 → 健診ナビの画面で対応」と一覧に出すだけにしていた。
- 安全な順番:
  1. **いますぐ**: 受付JSONから「画面で付けるオプションの一覧（予約ID・受付番号・氏名・受診日・オプション・採血の有無）」を作る（読むだけ）。事務の人が健診ナビの画面で付ける
  2. **check119 の結果と江東微研への確認のあと**: 画面と同じものを作れると確かめられたら、プレビュー付きで自動化を考える

## 2. 画面でオプションを付けたときにできるもの

| 作られるもの | 分かっていること（check73〜76・waku_add の調べ） | まだ確かめていないこと |

## 4. 重複防止

| 場面 | 扱い |
|---|---|
| その予約に同じオプションがもうある（料金明細に同じコード、または検査の親の行がある） | 足さない（「すでにあり」） |
| オプションの中身の検査が、基本コースの枠にもうある（例: PSA がコースに入っている） | 足さずに知らせる。二重請求・二重依頼になりうるので人が判断（check119 の 11 で、新島で重なる検査があるかを見る） |
| 受付JSONの中で同じオプションが 2 回 | 1 回として扱う |
| 受付でオプションを中止した | 自動では消さない。知らせるだけ |

## 5. 同じ JSON を再取込したとき

- 4 の「すでにあり」で止まるので、何度流しても二重には足さない
- いつのファイルの何を足したかを、案件（series_id）ごとの記録に残す。同じ ファイル・revision は 2 回目以降は何もしない。古いファイルは止める
- 一度足したあとアプリで中止された場合は、知らせるだけ（消すのは画面で）

## 6. 対象の確かめ方（予約ID・氏名・受診日）

受付JSONに `navi.reservation_id`（健診ナビの PK_SEQ）を持たせ、次が全部合ったときだけ対象にする:

1. その予約ID の予約がある・取り消されていない（`F_TORIKESI = 0`）
2. 予約の受診日 ＝ 受付した日（`actual.checked_in_date`）
3. 予約の個人ID ＝ 事前登録のときの個人ID
4. 健診ナビの氏名 ＝ 受付アプリの氏名（空白を詰め、旧字を新字に揃えて比べる）
5. 事業所が新島の事業所

一つでも違えば「確認が要る」に回し、足さない。

## 7. 追加前のプレビュー（案）

`当日オプション確認.bat`（読むだけ。健診ナビには書かない）:

- 受付JSONをドラッグ → 上の 6 の確かめと 4 の重複チェック → 一覧を出す
- 一覧の列: 状態 / 予約ID / 受付番号 / 受診日 / 氏名 / 追加するオプション（コード・名前） / 採血 / 中身の検査 / 料金
- 状態: **追加候補** / すでにあり / 基本コースと重なる / 対象の確認が要る / 対応表に無い記号 / 中止
- 血液のものを先頭に並べる（検体依頼の前に付けるため）
- 一覧は院内の PC の out に Excel で出す。事務の人はこれを見て健診ナビの画面でオプションを付ける

自動で書き込む版を作るのは、check119 の結果を見て、画面と同じものを作れると確かめてから（江東微研にも、料金明細と検査の行をツールで作ってよいか確認する）。

### 画面でオプションを付けたときにできていたもの

- 料金明細 `T_RYOUKIN`: 連番 2 以降に 1 行。`F_ADD_DEL = 2`（追加）、`DANTAI_RYOUKIN` = 団体料金、`KOJIN_RYOUKIN = 0`、`GOUKEI` = 合計、摘要は空

### 重複

- 新島の 11 月の予約には、まだどのオプションも付いていない（料金明細・検査の親の行とも 0）→ 当日の申込はすべて「追加」になる
