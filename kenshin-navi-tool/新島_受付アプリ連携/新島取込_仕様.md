# 新島取込ツール 仕様（Codex 向け）

作成 2026/11/16。新島（2026/11/22 受診、約 119 人）の受付アプリが出す JSON を、健診ナビ（SQL Server）の**既存の予約**へ反映するツールの仕様。
福生用の `受付結果取込.ps1` を手本にするが、**福生のファイルは一切変えず、新島用を別ファイルで作る。**

---

## 0. 絶対に守ること

1. **健診ナビ本体・帳票テンプレート・マスタは触らない。** 書いてよい表は `T_KENSIN`・`T_KOJIN1` の、下の 3 章で決めた列だけ。
   触ってはいけない: `T_COURSE1` `T_KIJUN1/2` `T_KIOU_HANTEI` `M_OPTION` `M_HENKAN_IRAI` `M_KENTAI_YOUKI` `T_KOMOKU` `T_SET2` `M_DANTAI` など全マスタ、`\\KNSV\KenshinNavi\CSV\検査センター.csv`、健診ナビのシステムフォルダ。
2. **`T_RYOUKIN`（料金明細）・`T_KENSA`（検査の行）には書かない。** 当日追加のオプションは一覧に出すだけ（6 章）。
3. **予約を新しく作らない・取り消さない・受診日を動かさない。**
4. 書く前に必ず **プレビュー → `Y`**。`backup\` に書く前の値と「元に戻す UPDATE 文」を残す。**1 つのトランザクション**でまとめて書き、**applock** を取り、書いた後に読み直して確かめる。
5. 福生のファイル（`受付結果取込.ps1/.bat`、`予約取込Excel作成.ps1/.bat`、`福生取込*.ps1/.bat`、`form/fussa_*.csv`、`backup/受付結果取込_前回.txt`）は**変更しない**。
6. 健診結果・氏名は要配慮個人情報。**外部サービスへ送らない**。ログ・画面に出す氏名は院内 PC の中だけ。チャットや Git には氏名を入れない（`out/`・`backup/` は git 管理外）。
7. 本番 DB で試さない。まずダミー JSON でプレビューのみ。本番の JSON を流すのは利用者が `Y` を押したときだけ。

## 2. 入力 JSON

受付アプリ（新島用。福生アプリの写しを別 DB で動かす）が出す。福生の形（`people[].id / identity / planned / actual / derived`）を基本に、新島用に `navi` を足す。

```json
{
  "schema_version": "1.0",
  "series_id": "niijima_2026",
  "exported_at": "2026-11-22T09:30:00+09:00",
  "revision": 12,
  "reception_version": "…",
  "counts": { "total": 119, "checked_in": 40 },
  "warnings": [],
  "people": [
    {
      "id": "N0001",
      "navi": {
        "reservation_id": "2007xxx",
        "kojin_id": "123456",
        "dantai_cd": "…",
        "course_cd": "…",
        "option_codes": []
      },
      "identity": { "name": "山田 太郎", "kana": "ﾔﾏﾀﾞ ﾀﾛｳ", "birth_date": "1970-01-01", "gender": "男" },
      "planned":  { "company": "…（新島）", "date": "2026-11-22", "time": "09:00～09:15", "course": "…", "options": [] },
      "actual":   { "checked_in_date": "2026-11-22", "reception_number": "12", "course": "…",
                    "options": ["OP0005", "OP0007"], "stool_count": 2, "exam_changes": {} },
      "derived":  { "is_cancelled": false, "date_changed": false, "course_changed": false,
                    "options_added": ["OP0005", "OP0007"], "options_removed": [] }
    }
  ]
}
```

- `series_id` は **`niijima_2026`** 固定（会期で分けるなら `niijima_2026_11`）。違う値なら止める。
- `navi.reservation_id` = 健診ナビ `T_KENSIN.PK_SEQ`。`navi.kojin_id` = `KOJIN_ID`。**これは事前登録のときに健診ナビから出した値をそのまま持ち回る**（`新島受診者一覧.bat` が出す Excel の「予約ID」「個人ID」列）。
- `id`（受診者ID。`N0001`…）は受付アプリの中だけの番号。健診ナビの `KOJIN_NO`（受診者番号）とは**別物**。混ぜない。
- `actual.options` / `derived.options_added` は**健診ナビのコード**（`OP0001`〜`OP0009`）で持つ。記号を使うなら `form/niijima_option_map.csv`（記号 → コード・名称・採血の有無）を作って読み替える。
- 受付していない人は `actual` が無い（または `checked_in_date` が空）。

## 3. 対象の決め方（1 人ずつ）

JSON の `people` ごとに、健診ナビの予約を **`navi.reservation_id` で 1 件引く**（`WHERE PK_SEQ = @id`）。氏名での検索は**しない**（同姓同名事故を避ける）。
次の全部が合ったときだけ「対象」。1 つでも違えば「確認が要る」に回し、**何も書かない**。

| # | 確かめること | 違ったときの表示 |
|---|---|---|
| 1 | 予約がある・`F_TORIKESI = 0` | 予約が無い / 取消済み |
| 2 | `D_KENSIN` ＝ `actual.checked_in_date`（`-` → `/`） | 受診日が違う（予定 … → 実際 …）。**受付番号は入れない** |
| 3 | `KOJIN_ID` ＝ `navi.kojin_id` | 個人IDが違う |
| 4 | 健診ナビの `KANJI_SIMEI` ＝ `identity.name`（**空白を全部詰め、`Normalize(FormKC)` し、旧字→新字（﨑→崎 など `form_import.ps1` の既存の表）を揃えて**比べる） | 氏名が違う |
| 5 | `DANTAI_CD1` が新島の事業所（`M_DANTAI.MEISYO1 LIKE '%新島%' OR '%式根島%'`。語は `-Words` で変えられる） | 新島の団体でない |
| 6 | `derived.is_cancelled = false` | 受付で取消（健診ナビは取り消さない。知らせるだけ） |

受付番号の重複: 同じ受診日の `T_KENSIN.UKE_NO_KENSA` と `T_KANJA_G.KEN_NO` に同じ番号が**別の人**で入っていたら書かずに知らせる。

## 4. 書く内容（プレビューの行）

対象の人ごとに「書く列」を決める。全員分を先に一覧にして、`Y` を押すまで何も書かない。

| 列 | 入れる値 | 書かないとき |
|---|---|---|
| 受付番号 `UKE_NO_KENSA` | `actual.reception_number`（数字のみ。空なら書かない） | 健診ナビにすでに**同じ**番号 → 何もしない / **違う**番号 → 書かずに「違う」と表示 |
| カナ `KANA_SIMEI` | `identity.kana` を半角カナ・空白詰めに | 健診ナビが空でないとき |
| 生年月日 `D_SEINEN` | `identity.birth_date` → 健診ナビの形式（既存の列の値を見て合わせる。`yyyy/MM/dd`） | 健診ナビが空でないとき。違えば表示 |

プレビューの表の列: `状態 / 予約ID / 受付番号(新) / 受診日 / 氏名 / 書く列と 旧→新 / 注意`。
状態: **書く** / 変更なし / 確認が要る（理由）/ 取消 / 未受付。
件数のまとめ（書く・変更なし・確認が要る・取消・未受付）を最後に出す。

## 5. 同じ JSON を毎日・何度も流したとき（累積ファイル。冪等）

- `backup\新島取込_前回_niijima_2026.txt` に前回の `series_id / exported_at / revision / ファイル名` を残す（**福生の `受付結果取込_前回.txt` とは別ファイル**。series_id ごとに 1 つ）。
- 同じ `exported_at`・`revision` → 「前回と同じファイル」と表示。差分が 0 なら書かない。
- 前回より古い（`exported_at` が前、または `revision` が小さい）→ 止める。`-Force` で続行できる。
- 受付番号が同じ → 何もしない。カナ・生年月日は空のときだけ → 2 回目は何もしない。よって何度流しても二重には書かない。
- 受付アプリで受付番号を消した → 健診ナビの番号は消さない。
- 受付で取消・受診日変更・オプション変更 → 書かずに知らせる（6 章）。
- お知らせは「前回の取込から変わったもの」に印を付ける（前回の JSON の `people` を `backup\新島取込_前回_niijima_2026.json` に残して比べる）。全部出した上で、新しいものに ★。
- 対応表 `backup\対応表_niijima_2026.csv`（`id ↔ PK_SEQ ↔ KOJIN_ID`）を毎回上書き。照合には使わない（照合は `reservation_id`）。
- ロック名 `RECEPTION_IMPORT:niijima_2026`（福生と別）。

## 6. 当日追加のオプション（**書かない。一覧に出すだけ**）

### オプション一覧の作り方

対象の人（3 章で合った人）の `derived.options_added` / `options_removed` と、健診ナビの現状（`T_RYOUKIN.KOMOKU_CD` または `T_KENSA.KOMOKU_CD` にそのコードがあるか）を比べ、1 行 1 オプションで出す。

| 状態 | 条件 |
|---|---|
| **追加候補** | 受付で追加され、健診ナビにまだ無い |
| すでにあり | 健診ナビにそのコードがもうある |
| **中身が重なる** | OP0001 と OP0002/OP0003 を同時に申し込んだ（PSA・BNP が二重）。または中身の項目CDが基本コースの `T_KENSA` にもうある（便潜血 069245/069246 が基本コースに入っている人に OP0009） → 人が判断 |
| 中止 | `options_removed` にある（健診ナビからは**消さない**） |
| 対応表に無い | コードが `niijima_option_map.csv` に無い |

並び: **採血○を先頭**（検体依頼の前に画面で付けるため）、次に受付番号順。
出力: 画面の表 ＋ `out\新島_当日オプション_<yyyyMMdd_HHmmss>.xlsx`（または CSV）。列: `状態 / 予約ID / 受付番号 / 氏名 / オプションのコード・名称 / 採血 / 団体料金 / 注意`。院内 PC の `out\` に出すだけ。

## 7. 作るファイル（福生のファイルは触らない）

| ファイル | 役目 |
|---|---|
| `niijima_import.ps1` | 本体。`param([string]$Json, [string]$Words='新島,式根島', [string]$SeriesId='niijima_2026', [switch]$NoKana, [switch]$Force, [switch]$Commit, [switch]$Inspect)` |

| `backup/新島取込_<ts>_before.csv` / `新島取込_<ts>_undo.sql` | 書く前の値と、元に戻す UPDATE 文 |
| `新島_受付アプリ連携/README.md` | 使い方を追記 |

`-Inspect`: JSON の中身（件数・series_id・exported_at・revision・people の形）だけ表示して終わる。DB に接続しない。
`-Commit`: 確認なしで書く（通常は使わない。プレビュー → `Y` が基本）。

## 8. 試し方（本番に書かない）

1. `新島_受付アプリ連携/新島_事前登録_見本.json` を基に、`actual`・`derived` を足したダミー JSON を作る（予約ID は本番に無い `900001`〜）。
   `-Inspect` → 形が読めること。プレビュー → 全員「予約が無い」で止まり、**何も書かないこと**を確かめる。
2. 本番の予約ID を 1 件だけ入れたダミーで、プレビューの「書く列」が正しく出ることを確かめる（`Y` は押さない。`N` で終わる）。
3. 受付番号が別の人に入っているダミー、受診日が違うダミー、OP0001＋OP0002 を同時に申し込んだダミーで、「確認が要る」「中身が重なる」になることを確かめる。
4. 同じファイルを 2 回流して「前回と同じファイル」になること、古い `revision` で止まることを確かめる。
5. 本番の JSON は 11/22 の当日、利用者が流す。
