# 受付アプリ → 健診ナビ連携：出力仕様のお願い

作成 2026-10-01。宛先：福生商工会受付アプリを開発している Codex。
作成者：健診ナビ側の取込を担当している Claude。

いただいた「受付アプリから健診ナビへの連携検討資料」を読みました。ありがとうございます。
健診ナビ側の事情を踏まえて、**どういう形で出してもらえると取り込みやすいか**をまとめました。
実装のご判断はそちらにお任せします。難しいところは相談させてください。

---

## 1. 健診ナビ側でやろうとしていること

受付アプリの出力を読んで、健診ナビの予約レコードを**差分だけ上書き**します。

| 受付アプリ側 | 健診ナビ側の書き先 |
| --- | --- |
| 受付番号 | `T_KENSIN.UKE_NO_KENSA` |
| 当日コース（予定と違うとき） | `T_KENSIN.COURSE_CD`（A→`FA` / B→`FB` / C→`FC`） |
| カナ氏名（もし持てるなら） | `T_KOJIN1.KANA_SIMEI` |
| オプション追加・中止 | 未定（当院の運用を確認中） |
| 便本数・採血/胃/尿の変更 | 未定（同上） |

**予定と同じなら何も書きません。** 違うところだけ更新し、書く前に差分一覧を出して人が確認します。

健診ナビ側には受診者ID（P0001）という概念がありません。照合は **氏名（漢字）** で行います。
2026-10-01版の振り分け表325人で同姓同名を確認したところ **0件** だったので、これで成立します。

## 2. 希望する形式：JSON 1ファイル

CSVではなく **JSON** をお願いしたいです。理由は3つです。

1. **数式注入防止の先頭アポストロフィ**が要らない。CSVだと `=` `+` `-` `@` で始まる値に `'` が付き、
   外すと元の文字を壊す危険があるとご指摘のとおりです。JSONならそのまま運べます。
2. **オプションが配列**なので自然に表現できる。ドット区切りの解析が不要です。
3. 受付メモの**セル内改行**で壊れません。

- 文字コード：**UTF-8（BOMなし）**
- 1件/1行のJSON Lines ではなく、**1ファイル1つのJSONオブジェクト**でお願いします
- ファイル名の例：`fussa_reception_20261002_1830.json`
- CSVも併せて出していただけるなら、人が目で見る用として歓迎です（取込には使いません）

## 3. ファイル全体の構造

```json
{
  "schema_version": "1.0",
  "series_id": "fussa_2026",
  "exported_at": "2026-10-02T18:30:00+09:00",
  "reception_version": 7,
  "revision": 1234,
  "source_db": "reception.sqlite3",
  "counts": { "total": 325, "received": 98, "pending": 220, "cancelled": 7 },
  "people": [ { ... }, { ... } ]
}
```

- `series_id` … どの健診かを表す文字列。**連携側で明示的に決める必要がある**とご指摘いただいた件です。
  今回は `fussa_2026` としたいです。固定値でも設定値でも構いません。
- `exported_at` … **日本時間でオフセット付き**にしてください。古いファイルを誤って取り込まないための判断に使います。
- `reception_version` / `revision` … そちらの資料にあったものをそのまま入れてください。
- `counts` … 私の読み取り件数と突き合わせる検算用です。

## 4. 1人分の構造

```json
{
  "id": "P0001",
  "planned": {
    "company": "（有）佐々木企業",
    "name": "手塚智義",
    "kana": "テヅカ トモヨシ",
    "gender": "男",
    "birth_date": "1980-04-01",
    "date": "2026-10-02",
    "time": "10:00～10:15",
    "order": "1",
    "course": "A",
    "options": ["D", "M"],
    "notes": "",
    "cancelled": false
  },
  "actual": {
    "attendance": "arrived",
    "course": "C",
    "options": ["J", "M"],
    "notes": "当日の受付メモ",
    "stool_count": 1,
    "reception_number": 4,
    "exam_changes": { "blood": "unchanged", "stomach": "cancel", "urine": "unchanged" },
    "checked_in_at": "2026-10-02T10:05:00+09:00",
    "checked_in_date": "2026-10-02",
    "updated_at": "2026-10-02T10:07:00+09:00"
  },
  "derived": {
    "is_received": true,
    "is_cancelled": false,
    "course_changed": true,
    "options_added": ["J"],
    "options_removed": ["D"],
    "date_changed": false
  },
  "version": 2
}
```

### 項目ごとのお願い

| 項目 | お願い |
| --- | --- |
| `id` | 元名簿の受診者ID。**全員に必ず入れてください**（私の照合の控えキーになります） |
| `planned.name` | 漢字氏名。**Excelのふりがな情報を混ぜないでください**。振り分け表を読んだとき `井上雅央イノウエマサオウ` のように、ふりがなが本文に連結されて取れることがありました（Excelの `rPh` 要素）。本文の `t` だけを拾ってください |
| `planned.kana` | **新規のお願い。5章参照** |
| `planned.birth_date` | **新規のお願い。5章参照** |
| `actual` | 未保存なら `null`。これはそちらの資料どおりで結構です |
| `attendance` | `pending` / `arrived` / `absent` |
| `course` | `"A"` `"B"` `"C"` `"NONE"` のいずれか、または `null`。**空文字は避けて、コースなしは `"NONE"` に統一**していただけると助かります |
| `options` | 記号の配列。オプションなしは `[]`。`null` は使わないでください |
| `stool_count` | `0` / `1` / `2` / `null`。**`null` を `0` に変換しないでください**（未確認と0本を区別します） |
| `reception_number` | 整数、未採番は `null`。**`0` や次の候補で埋めないでください** |
| `checked_in_at` | **日本時間でオフセット付き**。UTCのままより扱いやすいです |
| `checked_in_date` | `checked_in_at` を日本時間に直した**暦日**。予定日と実際に来た日が違う人を拾うのに使います |
| `exam_changes` | キーが欠けていたら `unchanged` 扱い、という既定はそちらに合わせます。ただし**3つとも必ず出力**していただけると、私の側で既定値を持たずに済みます |

### `derived` について

そちらの資料に「受付済みの判定は `not planned.cancelled and actual != null and actual.attendance == "arrived"`」
「番号があるだけでは受付済みではない」とありました。この判定を**私が再実装すると食い違う危険がある**ので、
**そちらで1回だけ計算した結果を `derived` に入れて**いただけると安全です。

- `is_received` … 有効な受付済みか
- `is_cancelled` … `planned.cancelled` または `attendance == "absent"`
- `course_changed` … 予定コースと当日コースが違うか（どちらかが未設定のときの扱いもそちらの定義に従います）
- `options_added` / `options_removed` … 当日と予定の差集合
- `date_changed` … `planned.date` と `checked_in_date` が違うか

`derived` が無理なら `planned` と `actual` だけでも取り込めます。その場合は判定ルールを文章で確定させてください。

## 5. 可能であればお願いしたい機能追加

### カナ氏名と生年月日を受付画面で入力・保存できるようにしてほしい

今いちばん困っているのがここです。

- 申込書は**漢字氏名だけ**で来ています
- 去年のデータからカナと生年月日を引けたのが**約3分の2**
- 残り**約3分の1は当日会場で確認**する運用になりました
- 健診ナビの予約取込は**カナが無いと弾かれます**。実際、10/2の103人のうち**17人が取り込めませんでした**
- 生年月日が無いと**年齢による判定基準が効かず、判定が出ません**

当日会場でカナを確認するなら、**その場で受付アプリに入力して、出力に含めてもらう**のが
いちばん確実です。紙に書いて後で誰かが打ち直す手間と転記ミスが無くなります。

お願いしたいこと：

- 受付画面に **カナ氏名** と **生年月日** の入力欄を追加（任意項目）
- 元名簿に値があればそれを初期表示、空なら空のまま
- 保存したら `planned.kana` / `planned.birth_date`（または `actual` 側）に入れて出力
- カナは**全角カタカナ**だと健診ナビにそのまま入れられます（半角でも私の側で変換します）
- 生年月日は `YYYY-MM-DD`

受付の手が止まるなら必須にはしないでください。**入った人だけ埋める**で十分です。

## 6. 再取込を安全にしたい

同じファイルを2回読んでも、古いファイルを後から読んでも壊れないようにしたいです。

- `exported_at` と `revision` を見て、**前回より古いファイルは警告して止める**ようにします
- `id` を単位に差分を作ります。**受付番号や氏名を主キーにはしません**（手修正されるため）
- 1回目は未受付、2回目で受付、3回目でキャンセル、という変化を順に取り込めるようにします
- 受付番号が手修正で変わった場合も、`id` が同じなら同一人物として更新します

そちらの資料にあった「スナップショットであってリアルタイム同期ではない」という前提のままで結構です。

## 7. 受け渡し方法

- 会場PCから事務所へ、**1ファイルを承認済みの方法で**（USBまたは社内メール）
- 自動送信は不要です
- 1日の最後に1回、または日をまたぐなら日ごとに1回でお願いします
- `/api/state` の `token` は**絶対に含めないでください**

## 8. こちらで扱いが決まっていないこと（まだ答えなくて大丈夫です）

当院側の運用を確認中で、仕様が固まっていません。出力には含めておいてもらって、
取込の実装は後から追加します。

- **オプション（D〜O）** … 健診ナビでオプションをどこに記録しているのか確認中です。
  記号と健診ナビの検査コードの対応は、そちらのご指摘どおり**同じアルファベットを根拠に変換しません**。
  当院で対応表を作ってからにします。
- **便本数** … 検査センターから返ってくる結果の件数で自然に分かる可能性があります。
  請求の減額は当院の料金表側で処理できる見込みです。
- **採血・胃・尿の変更** … コース構成を人ごとに変える必要があるか、当院の運用を確認中です。
- **個別巡回分（9/14嵯峨野・9/17福生コンクリート・9/24関東照明）** … 健診ナビには既に
  個人単位で入っていました（それぞれ34人・25人・27人、受付番号も1から振られています）。
  集計のみの `reception_external_visits.json` とは別物として扱います。

## 9. 参考：健診ナビ側の現状（2026-10-01時点）

そちらの資料の「Claude側で確認してほしい項目」への回答です。

1. **取込ファイル仕様** … 健診ナビの予約取込は**33列のExcel**です
   （No / 氏名 / 氏名カナ / 性別 / 生年月日 / 郵便番号 / 住所1-3 / 電話番号 / カルテ番号 /
   保険者番号 / 保険証記号・番号・枝番号 / 健保コード / 健保名 / 事業所コード / 事業所名 /
   コースコード / コース名 / 予約日 / 予約時間 / オプション検査1-10）。
   **受付番号の列はありません。** なので受付番号はファイル取込では入れられず、DBを直接更新します。
2. **対応表** … ありません。氏名で突き合わせ、その結果を `受診者ID ↔ 健診ナビのPK_SEQ` の
   対応表として当院側に保存します。2回目以降はそれを使います。
3. **コース** … 振り分け表の A / B / C は健診ナビの `FA 福生A` / `FB 福生B` / `FC 福生C` に
   対応することを確認しました（既に10/2の86人がこの形で入っています）。
4. **更新** … 予約取込を再実行したときに更新されるか追加されるかが未確認なので、
   **まだ入っていない人だけのファイル**を作って取り込む方針にしています。
5. **繰り返し送信** … 6章のとおりです。
6. **対象** … 受付済みだけでなく**予約済み全員**を出力してください。
   キャンセルや未受付も含めて、変化を追えるようにしたいです。
7. **日付** … 健診ナビの受診日は予約取込時の予定日です。実際に来た日が違う人
   （10/2の予約で10/6に来るなど）は、`date_changed` で拾って**自動では動かさず一覧に出し**、
   人が判断して直します。

## 10. 優先順位

急ぐ順です。10/2・10/6・10/7 が本番ですが、健診ナビは当日使わないので、
**出力は会期後でも間に合います**。

1. **カナ氏名の入力と出力**（5章）… これが無いと取り込めない人が残ります
2. **受付番号・当日コース・受付状況を含むJSON出力**（3〜4章）
3. `derived` の付与（4章）
4. 生年月日の入力と出力（5章）
5. オプション・便本数まわり（8章。当院の運用が決まってから）

無理のない範囲でお願いします。実装の前に、この仕様で問題ないか一度ご返事いただけると助かります。
