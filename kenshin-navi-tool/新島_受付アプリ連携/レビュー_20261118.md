対象: `新島_Claudeレビュー用_20261118.zip`（option_preview 1.0/1.1/1.2、MSAA/UIA の診断、niijima_import 1.6）。
本番 DB への接続・書き込みはしていない。C# はこの環境でコンパイルできなかったため、**下の修正コードは未実行**（PowerShell 5.1 の SelfTest で確かめること）。正規表現だけは別に確かめた。

## 0. 先に結論

1. **option_preview 1.2 は、実機でまた `code_value_unavailable` で止まる可能性が高い。** 健診ナビの検査コードには `017101A`（6 桁＋英字）・`001217HC`（6 桁＋英字 2 つ）の形があり、1.2 の `ValidCode` はこれを通さない。「知らない形のコードが 1 つでもあれば全体を止める」設計が原因で、形を足していく直し方ではまた別の形で止まる。→ 2 章の修正（形で止めない・1 回の実行で全部の診断を出す）。
2. **niijima_import 1.6 は、3 日分の予約にすると全員が止まる。** 氏名で探すときに 3 日とも検索するので 1 人 3 件になる。JSON の予約ID は 1 日分しか指せない。→ 3 章（**個人ID＋実際の受付日**で 1 件に決める）。あわせて「1 人でも要確認がいると全件中止」「プレビュー待ちの間ずっと Serializable で鍵を持つ」も直す。
3. **オプションの一括反映は、いまの「1 人ずつ画面を開いて MSAA で押す」方式の延長では届かない。** 画面を開くところ（メイン一覧の検索・選択）が手作業のままなら、省けるのは「チェックを入れて << を押す 5 秒」だけ。完全自動にはメイン画面の操作・完了メッセージの処理が要り、11/22 までに安全に仕上げるのは難しい。→ 4 章（当日は「取込ツールの一覧を見て画面で付ける」を確実な線として確保し、一括化は根拠が揃った方式で）。
4. 追加の実機確認は **1 回にまとめた**（5 章。読むだけ 2 本）。

## 2. option_preview の修正（1.3）

### 方針

- **形で止めない。** 実施予定検査のコードは「どんな形でも読めれば良い」。止めるのは「読めない（空・例外）」「コードらしくない文字（日本語・空白入り・長すぎ）」だけ。
- **最初の 1 件で止めない。** 全行を読み切って、問題のあった行の番号と形を最大 20 件、形ごとの件数を全部、結果 JSON に出す（実値は出さない）。これで実機 1 回で a・b・c が分かる。
- **タブを確かめる。**「契約項目」が選ばれているときだけ候補の表として扱う。
- 空の行は「行のセルが全部空」のときだけ飛ばし、飛ばした数を出す。コードだけ空で名称がある行は止める。

## 3. niijima_import 1.6 → 1.7（3 日分の予約に合わせる）

### 止まる所（コードで確認）

| # | 箇所 | 何が起きるか |
|---|---|---|
| 1 | `Get-Reservation` の氏名検索が `D_KENSIN IN (@visit0…)`。`$script:MatchDates` に**全員の予定日と受付日が全部**入る | 3 日分の予約があると 1 人 3 件 →「予約照合が 1 件でない」。11/17 のテストで 1 人目が止まったのも同じ形（予約ID が JSON に無く、氏名検索が 1 件にならなかった） |
| 2 | `navi.reservation_id` があるとそれで引く | 22 日の予約ID を持った人が 23 日に来ると「日付変更待ち」になり、23 日の予約に当たらない |
| 3 | 「日付変更待ち」「確認が要る」が 1 人でもいると `全件中止` | 382 人の一括処理で 1 人のために全員が止まる |
| 4 | `BeginTransaction(Serializable)` のまま全員分を読み、`Read-Host` で Y を待つ | 待っている間、読んだ範囲に鍵が掛かり、**健診ナビの画面の保存が待たされる**。福生の `受付結果取込.ps1` はプレビューをトランザクションの外でやり、書くときだけ短く取る |

### 照合の決め方（D への回答）

**その日の予約を決める鍵は「個人ID（KOJIN_ID）＋実際の受付日」。** 予約ID は日ごとに違うので鍵にしない（ヒントとしてだけ使う）。

```powershell
function Get-Reservation($Connection,$Transaction,$Person,[string]$Day){
 # $Day = 処理する日 (yyyy/MM/dd)。この日の、取り消されていない、新島の団体の予約だけを見る。
 $sql=@'

       p.KANJI_SIMEI,p.KANA_SIMEI,p.D_SEINEN,d.MEISYO1
FROM T_KENSIN k JOIN T_KOJIN1 p ON p.KOJIN_ID=k.KOJIN_ID
LEFT JOIN M_DANTAI d ON d.DANTAI_CD1=k.DANTAI_CD1
WHERE k.D_KENSIN=@day AND k.F_TORIKESI=0
'@

```

`Get-Decision` 側:

- 1 件に決まったあと、**氏名・生年月日（両方にあれば）・団体が新島・`D_KENSIN = 受付日`** を全部確かめる（いまのチェックはそのまま使える）。
- `navi.reservation_id` があって見つけた予約の `PK_SEQ` と違っても**止めない**（3 日分では違うのが普通）。注意欄に「予約ID は別の日のもの」と出すだけ。`'予約IDが違う'` を止める理由から外す。
- 0 件 →「この日の予約が無い」、2 件以上 →「この日に同じ人の予約が複数」。**理由を分けて出す**（いまの 1 文では原因が分からない）。
- 「日付変更待ち」は 3 日分の方針では起きないので、状態から外してよい（起きたら「この日の予約が無い」）。
- 団体名は `M_DANTAI.MEISYO1` で見る（既存ツールは全部これ。`T_DANTAI1` に同じ列があるかは確かめていない）。

### 一括処理の形（3・4 の直し）

```
1. JSON を検証 (DB 接続なし)
2. DB を開く。トランザクションなしで全員分を読み、プレビューを作る
   - 書ける人 / 変更なし / 確認が要る(理由) / 取消 / 未受付(その日に受付していない人は対象外)
3. プレビューを表示・out に保存。「確認が要る」がいても、書ける人は書く対象に残す
4. Y のあと、短いトランザクション (ReadCommitted + applock) で:
   - 1 人ずつ: UPDATE T_KENSIN SET UKE_NO_KENSA=@new
               WHERE PK_SEQ=@pk AND D_KENSIN=@day AND F_TORIKESI=0 AND KOJIN_ID=@kid
                 AND (UKE_NO_KENSA IS NULL OR UKE_NO_KENSA=0)
     → 1 行でなければ全体をロールバック (プレビューの後に誰かが変えた)
   - 同じ日・同じ番号が別の予約に無いことを、書いた後にまとめて確かめる:
     SELECT UKE_NO_KENSA FROM T_KENSIN WHERE D_KENSIN=@day AND F_TORIKESI=0 AND ISNULL(UKE_NO_KENSA,0)<>0
     GROUP BY UKE_NO_KENSA HAVING COUNT(*)>1   → 1 行でもあればロールバック
5. コミット → before.csv / undo.sql / 前回の記録を保存
```

- `WHERE` に `D_KENSIN=@day` と `KOJIN_ID=@kid` を入れるのが「22 日の予約ID を 23 日の更新先に使わない」の最後の歯止め。
- 「確認が要る」の人は、直してから同じ JSON をもう一度流せば入る（書ける人は「変更なし」になるので二重に書かない）。

### 3 日分の方針で、先に確かめること（5 章の check121 の 10・11）

| 確かめること | なぜ |
|---|---|
| 3 日分の予約が**同じ個人ID**に付いているか（10b・10d） | 予約データ取込で日ごとに別の個人が作られていると、個人ID で当てられず、氏名＋生年月日に落ちる |
| 同じ日に同じ人の予約が 2 件ないか（10c） | あると全員「複数」で止まる |
| **受付番号の無い予約が検体依頼に出ないか**（11） | 3 日分の方針の前提。各日 382 件の予約のうち、来た人だけが依頼に出る必要がある。福生では「受付番号が無いと依頼に載らない」だったが、数字で確かめる |
| 来なかった日の予約（382×3 − 実人数 ≒ 760 件）の後始末 | 取消にしないと、統計・請求・未受診の一覧に残る。会期後に健診ナビの画面で取り消す一覧（読むだけで作れる）が要る |

## 4. オプションの一括反映 — どう実現するか

### いまの方式（1 人ずつ画面を開いて MSAA）の見立て

| 項目 | 見立て |
|---|---|
| 読み取り（A） | 2 章の修正で読めるはず。表の決め方・列数（4 列／8 列）・パネルの決め方は診断と合っていて妥当 |
| チェックを入れる（C） | DataGridView のチェックのセルの `DoDefaultAction` は値を切り替えるが、**アプリの `CellContentClick` は走らない**。健診ナビがクリックのイベントで内部の状態（黄色の判定・選択リスト）を作っていると、画面の見た目と内部がずれる。実機でしか分からない |
| 「<<」を押す（C） | ボタンの `DoDefaultAction` は実クリックと同じ処理が走る。ただし**完了メッセージ（モーダル）が閉じるまで呼び出しが返らない**。別スレッドで押し、もう 1 本でメッセージの文言を確かめて閉じる作りが要る |
| 対象 1 名だけ（C） | 「他事業所の同じコースにも反映」が OFF、候補の表でチェックが入っているのが目的の 1 行だけ、を押す直前に読み直す。チェックの状態はセルの値（`True`/`False`）で読める |
| 本人確定（D） | 画面の文字（氏名・団体・日付）だけでは予約を確定できない（依頼文のとおり）。**押した後に DB を読んで確かめる**のが確実: その予約ID の料金明細に目的のコードが 1 行増え、同じ日のほかの予約には増えていない |
| 次の人へ（E） | メイン一覧の検索・選択・「検査追加/取消（個別）」を開く操作が未調査・未実装。ここが手作業のままなら、自動化で省けるのはチェックと << だけで、**手で付けるのとほとんど変わらない** |

→ **11/22 の本番にこの方式の「一括」を間に合わせるのは勧めない。** 調査用としては 2 章の修正で読めることを確かめる価値はある。

### 実現の道（3 つ）

| 道 | 中身 | 一括か | 根拠の状態 | 危険 |
|---|---|---|---|---|
| **A. 一覧を見て画面で付ける** | 取込ツールが出す「当日オプション一覧」（採血を先頭・受付番号順・重なりの注意つき）を見て、事務の人が画面で付ける | 一覧は一括、入力は手 | **実績あり**（福生・これまでの新島） | 最小 |
| **B. DB に直接、画面と同じ行を作る** | 料金明細 1 行＋検査の親の行＋中身の行を、プレビュー・バックアップ・トランザクション・元に戻す SQL つきで書く | **一括** | check119/120 で形は半分分かっている。残り（連番 99・印の列・セットの中身）は **check121 で分かる**。テスト 2 名に画面で足した実物と、ツールが作る行を 1 列ずつ比べて一致を確かめる | 画面の処理の再現。料金の合計行を間違えると請求に響く。検体依頼に出るかは実機で確かめる |
| **C. 画面操作の完全自動** | メイン一覧から人を開く → チェック → << → メッセージ → 閉じる、を全員分 | 一括（遅い） | メイン画面は未調査。モーダル・フォーカス・途中停止の扱いが要る | 画面が少しでも違うと止まる／別の人を開く危険。健診ナビを他の人が使えない |

### 勧める進め方

1. **当日（11/22〜24）は A を確実な線として確保する。** 受付番号は取込 1.7 で一括、オプションは一覧を見て画面で付ける。1.6 の一覧（`Get-OptionRows`）はそのまま使える。
2. **一括化は B を、根拠が揃ってから。** 5 章の check121 の結果が出れば、作る行が確定する。そのうえで、
   - テスト 2 名のうち 1 名（まだ付けていない方）にツールで OP0001 を足し、画面で足したもう 1 名と**全列を比べる**
   - 健診ナビの画面でその人を開き、実施予定検査・料金（14,300 円）・黄色の表示が画面で足したときと同じになるかを見る
   - 検体依頼に PSA・NT-proBNP が出るかを見る（検査会社には送らない）
   - ここまで一致して初めて本番に使う。**一致しなければ B はやめて A のまま**
3. C は来年に向けた調査として続けるなら、まずメイン一覧の構造を取る（5 章の 3）。

※ 依頼文の「DB 直接 INSERT はスキーマや業務処理が不明なので行わない」は、根拠が無い段階の判断として正しい。B は「不明」を check121 と行の比較で埋めてから判断する、という提案。**新島の請求を健診ナビから出すかどうか**で要る行が変わる（出さないなら料金明細を作らず検査の行だけ、という石屋のときの形もある）ので、これは利用者に決めてもらう必要がある。

### どの道でも共通の設計（E）

- 入力は JSON 1 つ＋処理する日。対象は「その日に受付した人」だけ。取消・未受付・別の日の予約には触らない。
- 1 人ずつ: 3 章の照合で予約を 1 件に決める → その予約の現状（料金明細・検査の行のコード）を読む → 追加候補／すでにあり／中身が重なる／対応表に無い、に分ける。
- **重なりは止める**: OP0001 と OP0002・OP0003、便潜血が基本コースにある人の OP0009。機械では足さず一覧に出す。
- **中止は消さない**: 受付で中止になったオプションは一覧に出すだけ。
- プレビュー（画面＋out の CSV）→ Y → 実行。実行の直前に 1 人ずつ読み直し、プレビューと違っていたらその人は飛ばして一覧に出す。
- 履歴: `backup\新島オプション_<日付>_<時刻>.csv` に「予約ID・コード・結果（足した／すでにあり／飛ばした理由）」。同じ JSON をもう一度流すと「すでにあり」で何もしない（冪等）。途中で止まっても、もう一度流せば残りだけ進む。
- 検体依頼が出た後（`T_KENSIN.F_IRAI = '1'`）の予約には足さず、「追加依頼が要る」と出す。
